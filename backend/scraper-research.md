# Snapchat scraper — OSS & approach research

Date: 2026-05-14
Goal: determine whether there is a workable way to **periodically pull friends'
snapscores from the backend** using our secondary account.

---

## TL;DR

There are three main approaches; **all three hit a practical wall**.

| Approach | Status | Why? |
|---|---|---|
| **A. Generate the Argos token in pure Python** (`riyadmondol2006/snapchat-argos-analysis`, Reversesio) | ❌ Non-starter | Hardware-backed attestation (SafetyNet/DeviceCheck) can't be produced in software. The repo explicitly says "NOT a working token generator". Reversesio's "Att-Token Python" post works with a `dummy Att message`; there's no validation against a real server. |
| **B. Web scraping (`web.snapchat.com`)** | ❌ No data | Snapchat help docs: "You can only access friends … in the Snapchat mobile app." Snapscore is never shown on the web. Even the `SnapFriends` lib only pulls bitmoji, no snapscore. The friends list is never rendered in the web client → there's no data to scrape. |
| **C. Frida bridge** (live signing on a mobile device) | ⚠️ Technically possible, high maintenance in practice | A rooted Android emulator + Snapchat APK + Frida server would have to run permanently. The backend asks the emulator to sign every request. **Cost**: a 24/7 emulator instance, re-doing the Frida hooks on every Snapchat update, bypassing anti-Frida detection. |

Within the POC window (1-2 weeks), no approach other than **C** is viable. And
**C** itself carries a genuine multi-month maintenance burden.

## Detailed findings

### A. Pure-Python Argos token generation

#### `github.com/riyadmondol2006/snapchat-argos-analysis`
- January 2025, months of analysis on Snapchat Android v13.51.0.56.
- 3 Python files (`argos_token_generator.py`, `enhanced_token_generator.py`, `token_simulator.py`).
- From the repo description: **"This is NOT a working token generator"** and **"Tokens generated by the simulator are NOT valid for Snapchat's servers"**.
- Reason: the private keys are hardware-protected (TEE/Secure Enclave), Python can't reach them.

#### Reversesio "How to Generate a Snapchat Att-Token Using Python" (February 2025)
- Encrypt the `Att` message with AES-GCM, base64url-encode it.
- Depends on PyCryptodome.
- The article **does not** show validation against a real Snapchat server; it says itself that it uses a "dummy Att message".
- The hardware attestation part is again missing → the server will most likely reject it.

**Conclusion**: this path is closed.

### B. Web scraping

#### `web.snapchat.com` capabilities (official Snapchat support)
- Web client: chat, send/receive snaps, AR Lenses, Memories.
- **No friends list**, no Profile page (snapscore lives on the profile).
- "You can only access friends and other Snapchatters' Profiles in the Snapchat mobile app." (Snapchat help)

#### `github.com/quintindunn/SnapFriends`
- The active user opens DevTools on `web.snapchat.com`, manually copies `friends.json`, and feeds it to the script.
- Output: bitmoji + display name. **No snapscore.**
- Last commit: Dec 2022, archived.
- Unclear whether it still works in 2025.

**Conclusion**: there is **no** access to friends' snapscores on the web; this
path is closed for lack of data.

### C. Frida bridge (live signing)

#### Architecture
```
Backend (Python)                 Virtual device (Android emulator)
─────────────────                ───────────────────────────────
fetch_friends() ──HTTP───────►   Frida server + hook script
                                 │
                                 ├─► Snapchat app (logged in)
                                 │   - the signing function is called
                                 │   - the hook captures the headers
                                 │
                ◄──HTTP────────  returns: signed headers
signed request to the Snapchat API
```

#### There is no single comprehensive OSS project that does this
- `pyrosec/snapchat-ssl-unpinning` — a Frida script for SSL pinning bypass only. No signing handlers.
- The "Casper" service (an old paid signing service) is now dead.
- This approach would have to be built from scratch.

#### Risks
- **Anti-Frida detection**: the Snapchat APK detects Frida and may ban the account.
- **APK updates**: hook offsets change on every major release → the hook script must be updated.
- **Emulator ban**: if device ID / Play Integrity / SafetyNet detects the emulator, Snapchat may stop working; a real device may be required.
- **Legal/ethical**: this hits one of the harshest clauses of the TOS — anomaly detection could flag it to a team that reviews it manually.

**Conclusion**: technically possible, but absurdly expensive for a one-off POC.

## Strategic recommendation (honest)

The POC was given 1-2 weeks. The status of the three approaches above:

1. **A** can't be attempted (won't pass the server).
2. **B** can't be attempted (no snapscore on the web).
3. **C** could be attempted, but 1-2 weeks isn't enough; it needs a real device lab + continuous maintenance, and the output is still fragile.

**Alternative recovery paths** (the plan's "Phase 2-B" section didn't cover this;
but the reality comes down to):

- **Semi-automatic OCR**: the user occasionally opens Snapchat and shares a screenshot of the friends list, the iOS Vision framework extracts the snapscores with on-device OCR, the user confirms, and they're written to a batch endpoint. **This needs an extra view in the iOS UI** — the user said "don't touch iOS", so this path is off-limits for now too.
- **Speed up manual entry**: a daily push notification + a single screen with a form to quickly enter snapscores for all users side by side. Still needs an iOS UI change.
- **Give up on automatic tracking**: leave the feature as it is now (manual).

## POC live verification (2026-05-14)

The user approved approach C → a full POC setup was built on a Mac and Snapchat
13.92 was tried in an emulator.

### Infrastructure that was set up (working)
- macOS 26 Apple Silicon, Android Studio Emulator (Pixel 7, API 34, Google APIs arm64-v8a)
- `adb root` + `-writable-system` → install mitmproxy CA into /system/etc/security/cacerts
- `mount --bind /data/local/tmp/cacerts-copy /apex/com.android.conscrypt/cacerts` to override the apex CA store
- `frida-server` 17.9.8 running on the emulator (first with the default name, then renamed to `/data/local/tmp/.sysmonsvc` + port 31337)
- `mitmweb` 11.0.2 — 8080 proxy + 8081 web UI
- `frida -U -f com.snapchat.android --codeshare akabe1/frida-multiple-unpinning` → spawn succeeded, SSL pinning bypass active (`Bypassing TrustManagerImpl` logs seen for `aws.api.snapchat.com`, `cf-st.sc-cdn.net`, `bolt-gcdn.sc-cdn.net`)

### The wall it hit
- Snapchat splash → **`C14A: Service Unavailable`** modal → process self-terminates.
- Same result **even** when Frida is fully disabled and Snapchat is launched plain. So the blocker isn't Frida, it's the emulator itself.
- Interpretation: Snapchat 13.92 calls the Play Integrity API; on the emulator the `DEVICE_INTEGRITY` and `STRONG_INTEGRITY` verdicts fail. The attestation token is verified server-side — producing it on an emulator is impossible without a hardware-backed key. This is a block that can't be bypassed with reverse engineering.

### Conclusion
- The emulator path is **closed**. Phase 1b (traffic capture) couldn't even start before hitting the wall.
- Anyone who wants to continue the reverse engineering would need a physical rooted Pixel device from here on.
- At this point the user said "give up for now" → the current manual flow stays.
